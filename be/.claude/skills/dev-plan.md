# Dev Plan

You are a senior backend engineer and tech lead for this NestJS/Fastify + Prisma + PostgreSQL multi-tenant platform. Your job is to create a structured implementation plan with live task tracking before ANY code is written.

## Usage

```
/dev-plan <description>
/dev-plan "Add batch document re-parent endpoint with permission cascade"
/dev-plan "Fix org quota not decrementing on folder delete"
```

- `<description>` — one sentence describing the feature or bug to work on
- If no description is given, ask the user for it before proceeding

---

## Step 1 — Classify the work

Determine if this is:
- **FEATURE** — new capability that doesn't exist yet
- **BUGFIX** — existing behavior that is broken
- **REFACTOR** — restructuring code without changing behavior
- **CHORE** — dependency update, config, migration cleanup

> ⚠️ If this is a **BUGFIX**, remind the user: "Run `/dev-rca` first to document the root cause before starting this plan."

---

## Step 2 — Explore the codebase

Before writing the plan, read relevant files to understand:
- Which domain(s) under `src/domains/` will be touched, and which layer within it
  (controller, Feature class, service, DTO, Prisma schema)
- Existing patterns used in similar features — which `FolderService`/`EntityPermissionService`/
  `PlanFeatureService` helpers already exist and should be reused rather than reinvented
- Multi-tenancy implications — does every new query need `orgId`/`ownerId` scoping? Does a
  new endpoint need a new `EntityPermissionService` check or reuse an existing one?
- Whether this needs a Prisma schema change (write the migration file only — never run
  `pnpm prisma migrate ...`, the developer runs migrations manually)
- Whether this needs a new BullMQ job (`src/core/queue/`), a new cron job
  (`src/commands/`), or calls into the agent service via `BaseAgentService`
- Integration points — what calls what, and whether the frontend or agent repo needs a
  contract change on the other side
- Any existing `.spec.ts` tests that must stay green

Use `git diff main...HEAD` or `git log --oneline -10` to understand current branch context.

---

## Step 3 — Write the plan document

Save to: `docs/plans/{feature-name}/PLAN-{yyyy-mm-dd}-{slug}.md`

Derive `{feature-name}` from the domain/capability (e.g. `document-batch-reparent`); derive
`{slug}` from the description (3-4 words, lowercase, hyphens). One folder per feature — if
`docs/plans/{feature-name}/` already exists (e.g. from a prior RCA), reuse it.

Use this exact template:

```markdown
# Plan: {Title}

**Type:** FEATURE | BUGFIX | REFACTOR | CHORE
**Branch:** {current branch}
**Domain:** {src/domains/<domain>}
**Created:** {YYYY-MM-DD}
**Status:** 🟡 In Progress

> {One paragraph: what problem this solves and why it matters}

---
```

## Step 4 — Track tasks as you work

After creating the plan, **actively maintain the PLAN.md** as you implement:

- Mark tasks `[x]` as each one is done
- Update **Status** in the header:
  - `🟡 In Progress` — work has started
  - `🔴 Blocked` — waiting on something, add a "Blocked by:" note
  - `✅ Done` — all tasks complete, acceptance criteria met

- After completing ALL tasks run:
  1. `/dev-review` — ensure no FAIL items
  2. `/dev-test` — generate or verify tests
  3. Update status to `✅ Done`
